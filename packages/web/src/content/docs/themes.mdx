With OpenCode you can select from one of several built-in themes, use a theme that adapts to your terminal theme, or define your own custom theme.

By default, OpenCode uses our own `opencode` theme.

---

## Terminal requirements

For themes to display correctly with their full color palette, your terminal must support **truecolor** (24-bit color). Most modern terminals support this by default, but you may need to enable it:

- **Check support**: Run `echo $COLORTERM` - it should output `truecolor` or `24bit`
- **Enable truecolor**: Set the environment variable `COLORTERM=truecolor` in your shell profile
- **Terminal compatibility**: Ensure your terminal emulator supports 24-bit color (most modern terminals like iTerm2, Alacritty, Kitty, Windows Terminal, and recent versions of GNOME Terminal do)

Without truecolor support, themes may appear with reduced color accuracy or fall back to the nearest 256-color approximation.

## System theme

The `system` theme is designed to automatically adapt to your terminal's color scheme. Unlike traditional themes that use fixed colors, the _system_ theme:

- **Generates gray scale**: Creates a custom gray scale based on your terminal's background color, ensuring optimal contrast.
- **Uses ANSI colors**: Leverages standard ANSI colors (0-15) for syntax highlighting and UI elements, which respect your terminal's color palette.
- **Preserves terminal defaults**: Uses `none` for text and background colors to maintain your terminal's native appearance.

The system theme is for users who:

- Want OpenCode to match their terminal's appearance
- Use custom terminal color schemes
- Prefer a consistent look across all terminal applications

## Using a theme

You can select a theme by bringing up the theme select with the `/theme` command. Or you can specify it in `tui.json`.

```json title="tui.json" {3}
{
  "$schema": "https://opencode.ai/tui.json",
  "theme": "tokyonight"
}
```

## Custom themes

OpenCode supports a flexible JSON-based theme system that allows users to create and customize themes easily.

---

### Hierarchy

Themes are loaded from multiple directories in the following order where later directories override earlier ones:

1. **Built-in themes** - These are embedded in the binary
2. **User config directory** - Defined in `~/.config/opencode/themes/*.json` or `$XDG_CONFIG_HOME/opencode/themes/*.json`
3. **Project root directory** - Defined in the `<project-root>/.opencode/themes/*.json`
4. **Current working directory** - Defined in `./.opencode/themes/*.json`

If multiple directories contain a theme with the same name, the theme from the directory with higher priority will be used.

---

### Creating a theme

To create a custom theme, create a JSON file in one of the theme directories.

For user-wide themes:

```bash no-frame
mkdir -p ~/.config/opencode/themes
vim ~/.config/opencode/themes/my-theme.json
```

And for project-specific themes.

```bash no-frame
mkdir -p .opencode/themes
vim .opencode/themes/my-theme.json
```

---

### Theme format

A theme file is a JSON object with three members:

- **`$schema`** (optional) - Points at `https://opencode.ai/theme.json` for editor autocompletion. It is informational and never affects behavior.
- **`defs`** (optional) - Named color constants you can reference elsewhere in the file.
- **`theme`** (required) - The actual theme: a map of **element names** to style entries.

Elements are addressed by dotted names, one per rendered UI surface. Each entry declares an optional foreground (`fg`), background (`bg`), and set of text `attributes`:

```json title="my-theme.json"
{
  "$schema": "https://opencode.ai/theme.json",
  "theme": {
    "dialog.title": {
      "fg": "#ffffff",
      "attributes": ["bold"]
    },
    "message.user.body": {
      "bg": "#1a1a2e"
    },
    "prompt.extmark.paste": {
      "fg": "message.user.body",
      "bg": "warning",
      "attributes": ["bold"]
    },
    "thinkingOpacity": 0.6
  }
}
```

An entry with only some channels set is a **partial override**: the unset channels keep the catalog defaults for that element. A present `attributes` array **replaces** the element's default attribute set wholesale - it does not merge. To remove a default attribute, list only the ones you want; to clear all attributes, use an empty array.

#### Attributes

The `attributes` array accepts exactly these values:

`bold`, `dim`, `italic`, `underline`, `blink`, `inverse`, `hidden`, `strikethrough`

Each value may appear at most once per entry.

#### thinkingOpacity

`thinkingOpacity` is a number between `0` and `1` (default `0.6`) that multiplies the foreground of every reasoning block, including its header, and the alpha of the subtle syntax colors. It is a scalar of `theme`, never part of an element entry.

---

### Color values

Every `fg` and `bg` value (and every `defs` constant) accepts:

- **Hex colors**: `"#ffffff"`, with 3, 4, 6, or 8 digits - `"#f0f"`, `"#8015"`, `"#2eff6a"`, `"#00000096"` (the last pair of digits is the alpha channel)
- **ANSI colors**: `3` (0-255) - resolved through a fixed color table, so your terminal's palette is never consulted
- **No color**: `"none"` uses the terminal's default color, `"transparent"` is fully transparent
- **References**: a name that resolves to another color (see below)
- **Dark/light variants**: `{"dark": "#000000", "light": "#ffffff"}` - both arms are required, and the arm matching the active mode is used

#### References

A **dotless** reference name (letters, digits, and underscores, starting with a letter) resolves against the file's `defs` first, then the built-in palette. A **dotted** reference must be a catalog element name and resolves **channel-wise**: an `fg` reference takes the referenced element's resolved foreground, a `bg` reference takes its resolved background. Attributes never flow through a reference.

```json
{
  "defs": {
    "ink": "#101010"
  },
  "theme": {
    "dialog.body": { "fg": "ink" },
    "dialog.title": { "fg": "dialog.body" },
    "prompt.text": { "bg": "dialog.title" }
  }
}
```

In a v2 theme the palette contains the color names of the default built-in theme - names like `primary`, `text`, `backgroundPanel`, `diffAdded`, or `syntaxKeyword` (see the [legacy key table](#legacy-format-v1-deprecated) for the full list). This is why a partial v2 theme works without redefining base colors: any name you do not mention falls back to the default theme.

---

### Defs

The `defs` section is optional and it allows you to define reusable colors that can be referenced in the theme. A def holds a hex color, an ANSI index, `"none"`/`"transparent"`, or a reference to another def, a palette name, or an element.

---

### Terminal defaults

The special value `"none"` can be used for any color to inherit the terminal's default color. This is particularly useful for creating themes that blend seamlessly with your terminal's color scheme:

- `"dialog.body": { "fg": "none" }` - Uses terminal's default foreground color
- `"app.background": { "bg": "none" }` - Uses terminal's default background color

### Errors

A theme file that violates the format is rejected at load and the reason is surfaced to you. The file is excluded from the theme registry and the active theme falls back to the default built-in theme - a rejected file never renders partially. The possible reasons:

| Reason                 | Meaning                                                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| `PARSE_ERROR`          | The file is not valid JSON                                                              |
| `NOT_A_THEME`          | The file has no `theme` object                                                          |
| `MIXED_FORMATS`        | v2 element entries and legacy v1 color keys are mixed in one `theme` object - use one format per file |
| `UNKNOWN_ELEMENT`      | An element name is not in the catalog (the catalog is closed)                            |
| `UNKNOWN_ATTRIBUTE`    | An `attributes` array contains a value outside the eight known attributes                |
| `INVALID_COLOR`        | Malformed hex, an ANSI index outside 0-255, or a non-color value                         |
| `UNRESOLVED_REFERENCE` | A reference name matches nothing in `defs`, the palette, or the catalog                  |
| `CYCLIC_REFERENCE`     | A chain of references revisits a name                                                    |
| `INVALID_ENTRY`        | An element entry has a member outside `fg`/`bg`/`attributes`, or `attributes` is not an array |

Note that the published [JSON schema](https://opencode.ai/theme.json) still validates a file that mixes both formats, so editors keep offering completions for legacy files - opencode itself is stricter and rejects the mix with `MIXED_FORMATS`.

### Legacy format (v1, deprecated)

Themes used to be a flat map of camelCase color keys. These files still load: they are **auto-migrated** to the element format at load, and the migration is lossless - every surface renders exactly the colors it rendered before. Mixing legacy keys with element entries in one file is rejected (`MIXED_FORMATS`), so new themes should use the element format exclusively.

```json title="legacy-theme.json"
{
  "$schema": "https://opencode.ai/theme.json",
  "theme": {
    "primary": { "dark": "#88C0D0", "light": "#5E81AC" },
    "background": { "dark": "#2E3440", "light": "#ECEFF4" }
  }
}
```

A v1 file that sets only some keys is fine too: missing palette names fall back to the default built-in theme. Six keys that never reached a rendered surface (`diffHunkHeader`, `markdownHorizontalRule`, `markdownListEnumeration`, `markdownImage`, `markdownImageText`, `markdownCodeBlock`) are ignored at migration.

### Element catalog

The catalog below lists every addressable element - it is a closed set, and a theme naming an element outside it is rejected with `UNKNOWN_ELEMENT`. Columns are per-channel defaults:

- `—` means the transparent color for `fg`/`bg` and the empty attribute set for attributes
- A backticked name is a [palette reference](#references) resolved against the default theme's palette
- `selected-foreground` is a computed contrast rule evaluated against the element's own resolved background
- `tint(...)` marks a computed blend
- Border elements paint single-color strokes on the `fg` channel
