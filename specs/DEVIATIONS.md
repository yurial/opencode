# Specification Deviations

- D1. `2026-10-28` — session-llm-serialization (with the unsettled-call amendment of core-tools-permissions R24)
  - Spec edit: new spec fixes the provider-facing serialization of unsettled tool calls — one successful tool result with the exact pending-result-placeholder literal, wording prohibitions against failure, interruption, and completion claims, applied symmetrically to the V1 history replay and the V2 history lowering; core-tools-permissions R24 delegates its pending/running clause to it.
  - Was: the V1 history replay serializes a pending or running tool part as an error result with the text `"[Tool execution was interrupted]"`, presenting a live call as interrupted; the V2 history lowering emits no result at all for a pending or running tool part, leaving a dangling tool call in the request.
  - Now: both runtimes serialize an unsettled tool call as exactly one successful tool result whose text is exactly PENDING_TOOL_RESULT_PLACEHOLDER, which states that the call is still executing, that the message is a placeholder and not the outcome, and that the call must not be retried or duplicated.
  - Code impact: `packages/opencode/src/session/message-v2.ts` (the pending/running branch of the replay lowering), `packages/core/src/session/runner/to-llm-message.ts` (the tool-result constructor fallthrough for pending and running states).
  - Tests: planned T1.1, T2.1, T2.3, T3.2 of session-llm-serialization; no conforming test exists yet.
  - Review focus: the placeholder replaces an error-typed result — confirm no provider path mistakes the successful placeholder for a real outcome; confirm the drain-start failing of abandoned tools owned by core-session is untouched; confirm placeholder substitution performs no durable write.

- D2. `2026-10-28` — tool-task (with the task highlight, jsonSchema example, and inventory row amendments in core-tools-permissions)
  - Spec edit: new spec fixes the task tool launch and completion contract — asynchronous launch by default with an immediate running result and the notification promise, the optional `wait` blocking argument, completion delivery as exactly one synthetic user message through the ordinary prompt admission of the host's single runtime graph (citing scheduler R8.3), and the description contract.
  - Was: the task tool blocks on the subagent run by default; asynchronous mode is the `background` argument gated behind `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS`, hidden from the advertised schema when the flag is off, with a description section appended only under the flag; no `wait` argument exists.
  - Now: asynchronous launch is the ungated default returning the running result of R1.2; `wait: true` opts into blocking settlement (R1.3); the former `background` argument is removed; completion delivery follows R2.1 through R2.4.
  - Code impact: `packages/opencode/src/tool/task.ts` (default path inversion, `wait` argument, flag and `background` removal, description composition), `packages/opencode/src/tool/task.txt` (description contract per R3.1), `packages/opencode/src/effect/runtime-flags.ts` and the `run.ts`/`experimental.ts` flag consumers; the `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS` row of config-parameters becomes inert for this tool and is removed with the code change.
  - Tests: planned T1.1, T1.3, T2.1, T2.3, T3.1 of tool-task; no conforming test exists yet.
  - Review focus: the default inversion changes every existing task call site and prompt guidance — confirm instructions that assume blocking semantics are updated; confirm flag removal leaves no dead flag handling; confirm the completion injection reaches the owning runner of the single runtime graph (the topology fix that unifies the scheduler and session services of one process).
